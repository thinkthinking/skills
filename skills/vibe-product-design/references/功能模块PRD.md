# 模式 B · 功能模块 PRD 写作指南

> **产出文件：** `features/<功能名 slug>/PRD.md`（单文档，不拆章、不需要合并脚本）
> **输入：** 已有产品背景（若存在模式 A 的 `PRD.md`/分章文件，直接读取引用） + 轻量问卷澄清结论 +
> 低保真原型图（存于同目录 `assets/`）。
> **作用：** 让团队里的每个角色，拿着**这一份文档**就能各自开工——不需要再追问你、不需要再开会对齐。

## 写给谁看，这份 PRD 就该让谁一眼看懂

这是本模板最重要的检验标准，写完自查一遍：

| 角色 | 该看哪一章 | 看完应该能回答的问题 |
| --- | --- | --- |
| UI/UX 设计师 | 第 4 章 | 每个界面/状态长什么样？关键交互怎么走？要复用哪些现有组件？ |
| 研发 | 第 5、6 章 | 业务规则是什么？状态怎么流转？异常怎么处理？要交付哪些功能点？ |
| 测试 | 第 7 章 | 要测哪些边界值、异常输入、权限组合？验收标准是什么？ |
| 产品经理 | 全篇，重点第 1、6 章 | 目标达成没有？范围有没有跑偏？能不能验收？ |

如果某一章的读者看完还要来问你"那具体是什么意思"，这一章就没写到位。

## 写作要求

- **收口，不做全量分析。** 不要重新分析用户画像、竞品、商业模式——那是模式 A 的事。这里只服务
  **这一个功能点**：它解决什么问题、怎么设计、怎么运转、边界在哪。
- **像造火箭说明书一样精确。** "优化交互体验"是废话；"提交按钮在表单未填完时置灰，鼠标悬停提示
  缺失字段"才是内容。每条业务规则、每个异常分支都要具体到可以直接转成代码逻辑或测试用例。
- **必画异常路径。** 核心流程图和业务规则里，每一步都问"这一步失败/超时/被拒绝会怎样"——这是
  和模式 A 第 04 章一致的原则，此处同样适用，不能省。
- **可追溯、不臆造背景。** 涉及现有产品的部分（已有页面、已有组件、已有数据）要基于用户提供的真实
  信息或已有 PRD 文件；不确定就问用户，不要编。外部事实（技术基准、合规要求等）仍遵循 SKILL.md
  的「联网核实」原则。
- **优先级/工作量/编码复用现成规范。** 见 `输出格式规范.md` 的 P0–P3、XXS–XXL、Low–Very High
  分级，不要重新发明一套。
- **原型图必须配文字说明。** 图只是辅助，图注要把关键交互点、状态差异讲清楚——设计师和研发都可能
  看不到图（渲染失败/离线阅读），文字要能独立说清楚逻辑。

## 1. 背景与目标
### 1.1 需求背景
为什么现在要做这个功能？谁提出的？有什么数据或反馈支撑？（引用真实信息，没有就问用户）

### 1.2 目标
做成什么样算成功？尽量可衡量（数字/行为指标），不要写"提升体验"这种空话。

### 1.3 非目标 / 明确不做
这一版**刻意不做**什么，避免范围蔓延、避免评审时被追问"那 XX 呢"。

## 2. 范围与约束
### 2.1 影响范围
涉及哪些**现有**页面、模块、角色、系统？新增了什么、改动了什么、删除了什么，列清楚。

### 2.2 前置依赖
依赖哪些现有能力/数据/第三方服务？依赖不满足会怎样？

### 2.3 假设与约束
做这个设计时假定为真、但未必验证过的前提，标 `[假设]`；已知的硬约束（性能、合规、技术栈）列出来。

## 3. 用户与场景
### 3.1 目标用户
这个功能服务谁？（若模式 A 已有用户画像，写"见 ../../PRD.md 第01章"+一句提要；没有就简述）

### 3.2 典型使用场景 / 用户故事
按最常见到最边缘的顺序列 2–5 个场景，每个场景一两句话说清楚"谁在什么情况下想干什么"。

## 4. 交互设计与产品原型
> 这一章是给 **UI/UX 设计师**看的：看完应该能直接开始出高保真设计稿。

### 4.1 关键交互流程说明
按状态/步骤描述用户怎么操作、界面怎么响应。每个关键界面/状态对应下面 4.2 的一张原型图。

### 4.2 低保真原型图
（原型图存于同目录 `assets/`，用相对路径引用；每张图配图注。图片生成规范见下方
「原型图生成规范」一节）

#### 图 1 · <界面/状态名称>
![<界面/状态名称>](assets/<文件名>.png)
- **这是什么：** 页面/弹窗/状态名，出现在哪个流程节点
- **关键元素：** 列出图上的关键区域/控件及其作用
- **交互说明：** 点击/滑动/输入后发生什么，对应哪个流程分支

（每张图重复上面的结构）

### 4.3 与现有设计规范的一致性
复用哪些现有组件/样式/交互模式？哪些是本功能新增、需要设计师新出的？

## 5. 业务逻辑与流程
> 这一章是给 **研发**看的：看完应该能直接排期写代码，不用再来问业务规则。

### 5.1 核心流程图
用 Mermaid 画，画法和示例见 `输出格式规范.md`「图表（Mermaid）」一节：涉及多角色/多系统协作用
「业务流程图」的时序图写法（`sequenceDiagram`，**必含 `alt/else` 异常分支**）；如果这个功能只是
单一角色在系统内部的状态流转，改用「功能架构图」的 `flowchart` 写法即可，同样要画出异常/失败分支，
不要只画快乐路径。

### 5.2 业务规则详解
把每条规则、计算逻辑、状态机讲清楚，具体到可以直接翻译成代码判断：
- 规则 1：<触发条件> → <处理逻辑> → <结果>
- 状态机（如适用）：状态清单 + 每个状态可以流转到哪些状态 + 触发流转的事件

### 5.3 权限与角色矩阵
| 角色 | 可见 | 可操作 | 说明 |
|---|---|---|---|
| … | … | … | … |

### 5.4 异常与边界处理
每个失败分支怎么处理（重试 / 回滚 / 提示文案 / 降级），逐条列出，不要笼统写"异常提示"：
| 异常场景 | 触发条件 | 系统行为 | 用户看到什么 |
|---|---|---|---|
| … | … | … | … |

## 6. 功能清单与验收标准
优先级、工作量、技术复杂度分级规范见 `输出格式规范.md`（沿用同一套 P0–P3/XXS–XXL/Low–Very High）。

**编码不必套用模式 A 完整的 L1–L4 四级体系**——模式 B 通常只是一个功能点，套四级反而繁琐。规则：

- 若这个功能挂在某个已有模式 A 全量 PRD 之下、且那份 PRD 里已经给这块业务定过 L1 模块码（如
  `PAY`），**复用那个 L1 码**，后面接两位流水号即可，如 `PAY-01`、`PAY-02`……
- 若没有可复用的 L1 码（没有模式 A 全量 PRD，或这次是全新模块），从功能名提炼一个 2–3 位大写字母
  前缀（如"降噪模式切换"→`ANC`），同样接两位流水号，如 `ANC-01`。
- 每个 ID 对应一条可独立验收的用户故事，不需要再往下拆 L2/L3/L4——这一份 PRD 本身就是最小颗粒度。

| ID | 描述（用户故事） | 优先级 | 工作量 | 验收标准 |
|---|---|---|---|---|
| ANC-01 | 作为…我想要…以便于… | P0 | S | Given <前提> When <操作> Then <预期结果> |

验收标准统一用 **Given-When-Then**（给定前提 - 触发操作 - 预期结果）格式，方便测试直接转成用例，
也方便 PM 验收时逐条打钩。

## 7. 测试关注点与边界用例
> 这一章是给 **测试**看的：看完应该能直接写测试用例，不用再来确认边界在哪。

专门列出容易漏测的边界，按类型分组，每条给出"输入/条件 → 预期结果"：
- **边界值：** 空值、最大/最小值、临界数量、极限并发数……
- **异常输入：** 非法格式、超长文本、恶意输入……
- **权限相关：** 越权访问、角色切换、登出重登……
- **并发/时序：** 同时操作、网络延迟、重复提交……
- **兼容性：** 不同终端/版本/网络环境下的表现（如适用）……

（可选，仅在涉及时写）需要新增/修改哪些数据字段、需要埋哪些点、用于回答什么业务问题。

## 原型图生成规范（用 `zenmux-image-generation` 生成）

在写第 4 章之前，先确定本功能要画哪几张原型图（对应关键界面/状态），一次性把所有 prompt 列出来
让用户确认，再统一生成，减少来回调用次数。

### 检查/安装 skill

先检查本机是否已装（常见安装路径如下，装法不同路径也会不同，找不到就直接跳到安装命令）：

```bash
ls ~/.agents/skills/zenmux-image-generation 2>/dev/null || \
ls <project-dir>/.agents/skills/zenmux-image-generation 2>/dev/null
```

未安装则用 `npx skills add` 安装（`npx` 需要本机已有 Node.js/npm 环境）：

```bash
# 项目级安装（默认，只在当前项目可用）
npx skills add https://github.com/zenmux/skills --skill zenmux-image-generation

# 全局安装（-g，所有项目都能用；只需装一次，之后新项目也不用重复装）
npx skills add https://github.com/zenmux/skills --skill zenmux-image-generation -g
```

装完再跑一遍上面的检查命令确认路径存在即可使用；后续 `zenmux-image-generation` 自身的用法、模型
选择、参数说明，以该 skill 自己的 `SKILL.md` 为准，这里不重复。

### Prompt 撰写要求（低保真线框图风格）

每条 prompt 都要显式声明风格约束，避免生成出精美视觉稿（那是高保真阶段的事）：

> 低保真线框图（lo-fi wireframe），灰阶/黑白配色，用简单的方框、线条、占位文字标签表示布局与
> 控件，不需要真实图片素材、不要精美渲染、不要拟物化质感，风格类似手绘线框稿或 Balsamiq 草图。
> 画面：<具体页面/状态描述，如"一个设置面板，顶部标题'降噪模式'，中间是三个单选卡片'关闭/通透/
> 强降噪'，底部一行小字提示当前电量消耗，右上角有返回箭头">

一个功能通常配 3–8 张图（覆盖主流程的每个关键节点 + 1–2 个关键异常/空状态），不要为了凑数画
无关紧要的界面，也不要漏掉核心的"啊哈"节点或异常提示状态。

### 输出路径（关键：必须落在本 skill 的产出目录下，方便 PRD 用相对路径引用）

生成时显式指定输出目录到当前功能的 `assets/` 子目录，不要用 `zenmux-image-generation` 自己的
默认输出路径：

```bash
--output-dir "<project-dir>/.context/requirements/vibe-product-design/features/<slug>/assets"
```

每个界面/状态生成 1 张即可（拿不准设计方向时可生成 2 张对比），不需要该 skill 默认的 4 变体。
生成完成后，在 4.2 节用相对路径 `assets/<文件名>.png` 引用（PRD.md 与 `assets/` 同级，相对路径
天然生效，换机器/换用户也不会失效)。

## 完成后

写入 `features/<slug>/PRD.md`，运行：

```bash
python3 <skill-dir>/scripts/format_feature_prd.py <project-dir>/.context/requirements/vibe-product-design/features/<slug>/PRD.md
```

规范化格式后，告诉用户文档路径、本次版本号、关键改动，以及原型图数量与存放路径。这份单文档
`PRD.md` 就是模式 B 的最终交付物。
